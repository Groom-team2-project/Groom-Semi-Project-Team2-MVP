# 회원 · 장바구니 · 포인트 설계와 기술 근거 (E 파트)

E 파트(회원·장바구니·쿠폰·포인트 + 캐싱) 중 **member / cart / point** 도메인에서 작성한 코드와
각 기술 선택의 근거를 정리한다. 원칙은 "버리지 않되 정당화한다" — 각 결정에 *왜/언제 필요한가*를 부여한다.

---

## 1. Member 도메인

### 무엇을 했나
- `PATCH /api/v1/members/me` — 프로필(이메일·닉네임) 부분 수정.
- `MemberService.updateMe` — 엔티티의 기존 `updateProfile()` 재사용 (null/공백은 무시하는 부분 수정).
- `getMe` 예외를 `RESOURCE_NOT_FOUND` → `MEMBER_NOT_FOUND` 로 통일.
- `MemberRepository.findByIdWithPessimisticLock` — 회원 종속 레코드(포인트 잔액)의 최초 생성 직렬화용.

### 근거
- **인증은 `@AuthenticationPrincipal AuthMember`(JWT)로 통일.** 초기엔 인증 필터가 없어 `X-Member-Id`
  임시 헤더를 썼으나, 파트 A의 JWT 필터가 들어온 뒤 실제 인증으로 교체했다. 임시 헤더는 호출자가 임의
  회원을 사칭할 수 있어 운영 전 반드시 제거해야 하는 값이었다.
- **부분 수정(PATCH) 의미론.** PUT(전체 교체)이 아니라 준 필드만 반영하는 게 프로필 수정의 자연스러운
  계약이다. 값 검증(`@Email`, `@Size`)은 요청 DTO에서, "빈 값은 무시"는 엔티티에서 담당해 책임을 나눴다.
- **예외 통일.** 도메인마다 리소스 없음을 제각기 표현하면 클라이언트가 분기하기 어렵다.
  회원 없음은 `MEMBER_NOT_FOUND` 하나로 통일했다.

## 2. Cart 도메인

### 무엇을 했나
- `CartEntity`(애그리거트 루트, 회원 1:1) + `CartItemEntity`.
- CRUD(`/api/v1/carts/**`) + 장바구니 주문(checkout).
- 회원별 Redis 캐싱 + 무효화.

### 2.1 엔티티 설계 — 애그리거트 루트

- **장바구니를 애그리거트 루트로 두고 항목 추가/삭제를 `CartEntity` 를 통해서만** 수행한다
  (`addItem`/`removeItem`/`clear`). 컬렉션 일관성(중복 상품 병합, 고아 삭제)을 엔티티 안에서 보장하기
  위해서다. `cascade = ALL, orphanRemoval = true` 로 항목 생명주기를 장바구니에 종속시킨다.
- **회원 참조는 `@OneToOne MemberEntity`(FK `member_id`, unique).** 처음엔 파트 A가 없어 `member_id`
  를 Long 컬럼으로 뒀다가, 회원 도메인이 들어온 뒤 FK 연관관계로 승격했다. 컬럼명이 그대로라 스키마
  변화는 없었다. "회원당 장바구니 하나"를 DB 유니크 제약으로 강제한다.

### 2.2 회원 데이터 격리

- 항목 조작(수량변경·삭제) 시 `item.getCart().isOwnedBy(memberId)` 로 소유권을 검증하고, 위반 시
  `CART_ITEM_FORBIDDEN`(403). **애플리케이션 레벨에서 남의 장바구니 항목 접근을 차단**한다.
- 근거: 항목 ID만 알면 남의 장바구니를 건드릴 수 있는 IDOR(권한 없는 직접 참조)을 막기 위함.
  단위 테스트(`CartServiceTest`)로 "다른 회원 항목 수정/삭제 차단"을 검증한다.

### 2.3 조회의 순수 읽기화 (캐싱 전제)

- 원래 `getMyCart` 는 "없으면 생성"(get-or-create)이라 **조회인데 쓰기를 유발**했다. 이러면 캐싱이
  불가능하다(조회가 부수효과를 가짐).
- **조회를 순수 읽기로 바꾸고, 장바구니 생성은 첫 담기(addItem) 시점으로 옮겼다.** 없으면 빈 응답을
  반환한다. 캐싱을 붙이려다 원래 설계의 군더더기(불필요한 쓰기)가 드러난 경우다.

### 2.4 N+1 방지

- `findByMemberIdWithItems` 는 `join fetch` 로 회원·항목·상품을 한 번에 로드한다. 장바구니 조회/주문
  전환처럼 항목 전체를 순회하는 경로에서 지연 로딩 N+1을 피하기 위함이다.

### 2.5 장바구니 주문(checkout) — 도메인 경계 존중

- checkout 은 재고/주문 도메인(파트 C)의 **공개 빌딩블록만** 사용해 조립한다:
  `StockEntity.reserve()`, `Order.pendingPayment(memberId, ...)`, `OrderItem`, `StockHistoryEntity.reserve()`.
  **해당 도메인 파일을 수정하지 않는다.**
- 근거: 기획서 §8 "E→C→D 는 하나의 흐름 → 인터페이스 사전 합의 필수". 남의 도메인 내부를 고치면 병합
  충돌·책임 혼선이 생기므로, 공개 API만 소비해 결합을 최소화했다. 파트 C가 예약(reserved) 모델을 확정한
  뒤 즉시 차감 → 예약 방식으로 맞춰 교체했다.
- 주문 생성 시 **주문자 회원 ID를 Order 에 기록**하므로, 이후 주문 내역 조회의 토대가 된다.

### 2.6 Redis 캐싱 — 상세 근거

| 결정 | 근거 |
|---|---|
| **분산락(RedisConfig)과 캐시를 분리** | 기존 `RedissonClient` 는 분산락(파트 C) 전용. 캐시는 Spring Cache 추상화 위에 별도 구성해, 서비스는 `@Cacheable`/`@CacheEvict` 만 쓰고 Redis 에 직접 의존하지 않는다. 락과 캐시가 서로의 설정에 얽히지 않는다. |
| **키 = memberId** | 장바구니는 회원별 데이터. 키를 회원으로 분리해 캐시가 섞이지 않게 한다. |
| **무효화가 주 수단, TTL은 안전망** | 장바구니를 바꾸는 모든 경로(담기·수량변경·삭제·비우기·checkout)에 `@CacheEvict`. TTL(30분)은 무효화 경로를 하나 빠뜨렸을 때 stale 이 영원히 남지 않게 하는 백스톱. |
| **`TransactionAwareCacheManagerProxy`** | put/evict 를 트랜잭션 **커밋 이후**에 반영. 커밋 전에 evict 된 틈으로 다른 조회가 옛 값을 재적재하거나, 롤백된 변경이 캐시에 새는 것을 줄인다. |
| **`LoggingCacheErrorHandler` (장애 흡수)** | Redis 장애 시 캐시 예외를 로깅 후 삼켜, DB 로 대체 가능한 요청까지 실패하지 않게 한다(가용성 우선). |
| **`CachingConfigurer.cacheManager()` no-arg `@Override`** | 인자 있는 `@Bean` 은 인터페이스를 오버라이드하지 못해 캐시 인프라가 프록시를 확실히 쓰지 못한다. 규약대로 no-arg 오버라이드로 명시적으로 적용. |
| **JSON 직렬화 + record DTO** | 값을 JSON 으로 저장해 `redis-cli` 로 읽히고 클래스 변경에 덜 취약. Spring Boot 4 는 Jackson 3 를 쓰므로 `@Jacksonized`(Jackson2/3 모호) 대신 응답 DTO를 **record** 로 두어 별도 설정 없이 역직렬화되게 했다. |
| **`PolymorphicTypeValidator` 로 역직렬화 화이트리스트** | 타입 정보(@class)를 저장해야 역직렬화가 되지만, 무제한 default typing 은 Redis 오염 시 가젯 공격에 노출된다. `org.example.groommvp.` 패키지로 좁혔다. |

> 트레이드오프: `@CacheEvict` 는 커밋 전 실행이 기본이라 이론상 stale 여지가 있어
> `TransactionAwareCacheManagerProxy` 로 커밋 후 반영으로 보정했다. 장바구니는 본인만 접근하는
> 데이터라 경합 위험 자체가 낮다.

## 3. Point 도메인

### 무엇을 했나
- `PointBalanceEntity`(point_balances, 잔액) + `PointHistoryEntity`(point_histories, 이력).
- `PointService`: 적립/사용/취소 **진입점** + 잔액/이력 조회.
- 조회 API: `GET /api/v1/members/me/points`, `/histories`.

### 3.1 잔액을 별도 테이블로 (이력 합산 아님)

- **현재 잔액을 `point_balances` 행에 저장**하고, 변동 이력은 `point_histories` 에 남긴다.
- 근거: 잔액을 매번 이력 합산으로 계산하면 동시 적립/사용에서 **음수 잔액·경합**이 생긴다. 잔액을 하나의
  행으로 두면 그 행에 **비관적 락**을 걸어 증감을 직렬화할 수 있다(재고/쿠폰과 같은 패턴).
- 회원(파트 A) 테이블을 건드리지 않으려고 `MemberEntity` 에 잔액 필드를 넣지 않고 포인트 도메인 안에서
  1:1 로 관리한다.

### 3.2 적립/사용은 "진입점"만 (공개 API 아님)

- 포인트는 사용자가 직접 늘리는 값이 아니라 **구매 확정 시 적립·결제 시 차감**되는 값이다. 그래서
  `earn`/`use`/`cancelUse` 는 공개 엔드포인트가 아니라 주문·결제 흐름(파트 C/D)에서 호출할 메서드로 두고,
  사용자에게는 **조회만** 노출했다(쿠폰 `useCoupon` 과 같은 방식).

### 3.3 최초 잔액 생성 경합 방지 — **회원 행을 잠근다** (§5.2 에서 수정됨)

- 잔액 증감은 read-modify-write 라 직렬화가 필요하다. 그런데 잔액 행은 **아직 없을 수 있다.**
- **존재하지 않는 행을 `SELECT ... FOR UPDATE` 하면 안 된다.** InnoDB 는 이때 레코드 락이 아니라
  **갭 락**을 잡는다. 갭 락끼리는 공존하지만 뒤따르는 INSERT 의 insert-intention 락과는 충돌하므로,
  **서로 다른 회원의 첫 적립끼리도 교착**한다. (32스레드 부하에서 6% 실패 — §5.2)
- 그래서 **반드시 존재하는 회원 행**을 잠근 뒤 잔액을 읽는다. 레코드 락만 잡혀 교착이 없고, 같은 회원의
  잔액 증감·최초 생성이 한 번에 직렬화된다.
- **순서가 중요하다.** REPEATABLE READ 의 읽기 뷰는 첫 *일반* 읽기에서 만들어지고 **락 조회는 만들지
  않는다.** 락을 먼저 잡고 읽어야 앞선 홀더가 커밋한 잔액이 보인다. 반대로 하면 낡은 스냅샷을 보고
  중복 생성을 시도한다.
- **병렬 최초 생성 테스트**(`PointServiceConcurrencyTest`, 20스레드 동시 적립 → 실패 0·합계 정확)로
  검증하고, 실제 MySQL 부하(`PartEPerformanceTest`)로 교착 0건을 확인한다.

### 3.4 취소 복구의 멱등성

- `cancelUse` 는 **호출자가 준 금액을 그대로 재적립하지 않는다.** 그러면 취소 이벤트가 재전송되거나 금액이
  원 사용액과 다를 때 잔액이 부풀려진다.
- 대신 (1) 해당 주문에 CANCEL 이력이 이미 있으면 **멱등 no-op**, (2) 없으면 그 주문의 **USE 이력에서 실제
  사용액을 읽어** 그만큼만 복구한다.
- 최종 방어선으로 `point_histories` 에 `(member_id, order_id, type)` 유니크 제약을 걸어, 재전송이 락을
  통과하더라도 CANCEL 이 주문당 한 번만 적재되게 한다. (order_id 가 null 인 행은 제약 대상이 아니라 수동
  적립 등에는 영향이 없다.)
- **적립/사용도 같은 방식으로 멱등이다.** 해당 주문에 이미 EARN/USE 이력이 있으면 아무것도 하지 않고 현재
  잔액을 반환한다. 결제 재시도로 포인트가 두 번 빠지지 않는다. 멱등 검사는 **회원 락을 잡은 뒤** 수행해야
  앞선 트랜잭션의 커밋을 본다.

## 4. 공통 기술 근거

### 4.1 왜 비관적 락인가 (낙관적 락이 아니라)
- 재고 차감·쿠폰 발급·포인트 증감은 모두 **read-modify-write** 로, 동시에 같은 값을 읽고 각자 갱신하면
  값이 어긋난다(초과 판매/발급, 잔액 오류).
- 기획서 §10: "단일 서버엔 비관적 락으로 충분, 분산락은 선착순 이벤트 한정." 짧은 임계 구역·높은 경합
  갱신에는 재시도 비용이 큰 낙관적 락보다 **행 단위 비관적 락(`FOR UPDATE`)** 이 단순하고 정확하다.
- 세 도메인이 같은 패턴(`findByIdWithPessimisticLock`)을 공유해 학습·리뷰 비용을 낮췄다.

### 4.2 트랜잭션과 캐시 정합
- 캐시 무효화는 트랜잭션과 어긋나면 stale 을 만든다. `TransactionAwareCacheManagerProxy` 로
  **커밋 이후에만 캐시를 반영**해, 롤백된 변경이 캐시에 남거나 커밋 전 재적재로 옛 값이 굳는 걸 줄였다.

### 4.3 도메인 경계 · 공용 코드 최소 변경
- 남의 도메인(재고·주문·회원 엔티티) 내부는 수정하지 않고 **공개 빌딩블록만 소비**했다. 공용 파일 변경은
  `ErrorCode`(상수 추가), `SecurityConfig`(인증 경로 추가), `build.gradle`(의존성) 등 **추가 위주**로 제한해
  병합 충돌과 책임 혼선을 줄였다.

## 5. 적대적 리뷰 반영 (2026-07-27)

cart · coupon · member · point 네 도메인을 적대적 관점으로 리뷰하고 발견한 결함을 수정했다.
성능 측정 결과는 [part-e-performance-report.md](part-e-performance-report.md) 에 따로 정리했다.

### 5.1 치명 · 높음

| # | 결함 | 조치 |
|---|---|---|
| C1 | 담기 응답의 `cartItemId` 가 항상 `null` — cascade INSERT 는 flush 시점이라 PK 미할당. 클라이언트가 방금 담은 항목을 바로 수정/삭제 불가 | 응답 생성 전에 `flush()` |
| C2 | `useCoupon` 이 락·버전 없이 동작 — 동시 요청 둘 다 "미사용"으로 읽어 **쿠폰 1장으로 2건 할인** | 보유 쿠폰 행 비관적 락 (`findByIdWithPessimisticLock`) |
| C3 | `checkout` 이 담은 순서대로 재고 락을 잡아, 같은 두 상품을 반대 순서로 담은 회원끼리 **교착** | 상품 ID 오름차순 정렬 후 예약 |
| C4 | 장바구니 최초 생성 경합 → 유니크 제약 위반 → **500** | 회원 행 락으로 직렬화 (§5.2 로 이어짐) |
| H1 | `earn`/`use` 에 멱등성 없음 — 결제 재시도 시 제약 위반이 500 으로 샘 | 락 이후 멱등 검사 + 제약 위반을 `POINT_ALREADY_PROCESSED` 로 변환 |
| H2 | `cancelUse` 의 "USE 이력 합산" 이 유니크 제약과 모순 (최대 1건인데 합산) | 리포지토리 반환을 `Optional` 로 |
| H3 | `cancelCouponUse` 가 주문 ID 를 받지 않아 **주문 A 취소가 주문 B 의 쿠폰을 되살림** | `cancelUseFor(orderId)` — `usedOrderId` 일치 시에만 복구, 멱등 |
| H4 | 정률 쿠폰 할인율 상한 없음 — `discountValue=1000` 이면 **전액 무료** | `DiscountType.validateDiscountValue` 를 엔티티 생성자에서 강제 (정률 1~100%) |

### 5.2 성능 테스트가 잡아낸 결함 — 갭 락 교착

C4 를 "없는 행을 `FOR UPDATE` 로 잠그고 만든다"로 고쳤더니, **실제 MySQL 부하에서 공유 자원이 전혀 없는
서로 다른 회원끼리도 교착**했다. (장바구니 33건 / 포인트 41건, 32스레드 기준 5~6%)

원인은 §3.3 에 적은 갭 락이다. **H2 에는 갭 락이 없어 기존 테스트로는 드러나지 않았다** — 이 결함은 이미
커밋된 상태였다(`4398df4`).

조치: **반드시 존재하는 회원 행**을 먼저 잠그고 그 뒤에 장바구니/잔액을 읽는다. 교착 33/41건 → **0건**,
처리량 저하 없음.

> 중간에 `REQUIRES_NEW` 로 생성을 분리하는 안을 시도했다가 폐기했다. 바깥 커넥션을 쥔 채 두 번째
> 커넥션을 요구해 **풀이 고갈되고 30초 행**이 걸렸다. 교착을 더 나쁜 장애로 바꾸는 셈이었다.

**교훈: 동시성 변경은 H2 그린만으로 검증했다고 말할 수 없다. 반드시 실제 MySQL 로 재검증한다.**

### 5.4 예약 재고 회수 (M3)

- 재고 도메인에 `StockEntity.release()` / `StockHistoryEntity.release()` 가 "결제 실패 또는 시간 초과로
  예약을 푼다"는 주석과 함께 **이미 있었으나 호출자가 없었다.** 그 빠진 호출자를 붙인 것이다.
- `OrderCancelService` 를 재사용하지 않았다. 그쪽은 `stock.increase()` 를 부르는데 이는 **실물 재고**를
  늘린다. 결제 완료 주문의 취소에는 맞지만 미결제 예약분에 쓰면 재고가 부풀려지고 `reservedStocks` 가
  그대로 남는다. 예약 회수에는 `release()` 가 맞다.
- **결제 완료와의 경합**: 주문 행을 잠근 뒤 상태를 다시 확인해, 락 대기 중 결제가 끝난 주문은 건드리지
  않는다. 재고 락은 `checkout` 과 같은 이유로 상품 ID 오름차순으로 잡는다.
- **주문마다 독립 트랜잭션**: 스케줄러가 비트랜잭션 상태에서 건별 호출한다. 한 건의 실패가 나머지 회수를
  막지 않고, 밀린 물량이 하나의 긴 트랜잭션으로 뭉치지 않는다.
- 운영 설정은 [pre-deploy-checklist.md](pre-deploy-checklist.md) §7 참고.

### 5.5 마이페이지 주문 내역

- `GET /api/v1/members/me/orders` (`MyOrderController`) — 인증된 본인의 주문만 최신순 반환. 회원 ID 를
  파라미터로 받지 않으므로 남의 내역을 요청할 방법 자체가 없다.
- 주문 항목은 주문 ID 목록으로 **한 번에** 조회해 N+1 을 피한다(`findByOrderIdsWithProduct`).
- 프론트 마이페이지에 주문 내역 카드를 추가했다. 상태 배지(결제 대기/구매 완료/취소됨/결제 실패), 주문
  상품별 수량·단가·합계, 주문 금액을 렌더링하고, 장바구니 주문 직후 자동 갱신된다.

## 6. 남은 통합 지점 (배포/통합 단계)

### 6.1 쿠폰/포인트를 주문·결제에 연결 — **설계 결정이 먼저 필요**

`useCoupon` / `use` / `cancelUse` / `cancelCouponUse` 는 진입점만 있고 **호출자가 없다.** 단순히 호출을
추가하면 되는 일이 아니라, 아래 결정이 선행되어야 한다.

**문제**: `PaymentService.pay()` 는 토스 결제 승인에 `order.getTotalPrice()` 를 그대로 넘긴다. 할인/포인트를
적용하면 **실제 결제 금액이 주문 금액과 달라진다.** 어느 값을 결제하고 어느 값을 주문에 남길지 정해야 한다.

| 선택지 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. 체크아웃 시점 적용** | `checkout` 이 `memberCouponId`/사용 포인트를 받아 할인된 금액으로 주문 생성 | 결제는 주문 금액만 보면 됨 (파트 D 무변경) | 결제 전 취소 시 쿠폰·포인트 복구 경로 필요 (회수 스케줄러에 얹어야 함) |
| **B. 결제 시점 적용** | `pay()` 가 쿠폰/포인트를 받아 최종 금액 계산 | 주문과 결제 관심사 분리 | `PaymentRequest`·결제 승인 금액 로직 변경 필요 (파트 D 변경) |

권장은 **A** 다. 이미 만들어 둔 예약 재고 회수 스케줄러가 "결제 안 된 주문 되돌리기" 자리를 잡고 있어,
쿠폰·포인트 복구를 같은 자리에 얹으면 되돌림 경로가 하나로 모인다.

어느 쪽이든 **파트 C/D 와 합의 후** 진행한다. 합의 없이 한쪽만 고치면 결제 금액이 어긋난다.
