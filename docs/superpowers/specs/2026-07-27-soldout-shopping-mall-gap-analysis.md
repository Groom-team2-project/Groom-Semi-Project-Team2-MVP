# SoldOut 쇼핑몰 완성도 점검 및 개선 백로그

- 작성일: 2026-07-27
- 작성 계기: 결제(D파트) 실제 E2E 테스트 중 발견한 공백을 팀 전체 관점으로 확장 점검
- 기준: **"동작하는 쇼핑몰"** — 구매자가 탐색 → 주문 → 결제 → 조회를 막힘 없이 할 수 있는가
- 대상 독자: 팀 전원 (다음 스프린트 논의 자료)

---

## 1. 한 장 요약

결제 흐름은 실제 토스 결제까지 검증 완료했다. 그 과정에서 **결제 자체가 아니라 그 주변**이 비어 있다는 게 드러났다.

```
[탐색]              [주문]           [결제]            [조회]
상품 목록 ✅        장바구니 ✅       토스 승인 ✅       주문 단건 ✅
검색 ✅             바로구매 ✅       결제 실패 ✅       주문 목록 ❌
카테고리 필터 ❌     재고 예약 ✅      환불 ✅            리뷰 ✅
상품 이미지 ❌       쿠폰/포인트 ❌    이메일 알림 ✅     별점 ❌
품절 표시 ❌
```

핵심 문제 3가지:

1. **주문 목록 조회 API가 없다** — 결제 후 주문을 다시 찾아갈 방법이 없다.
2. **카테고리로 상품을 찾을 수 없다** — 카테고리를 만들고 상품에 붙이는데 조회 조건에 없다. 기능이 죽어 있다.
3. **상품 이미지를 읽을 수 없다** — 등록·삭제 API만 있고 조회가 없어 화면이 실제 사진을 못 쓴다.

---

## 2. P0 — 없으면 쇼핑몰이 성립하지 않음

| # | 항목 | 현재 상태 | 필요한 것 | 담당 |
|---|------|-----------|-----------|------|
| P0-1 | **내 주문 목록** | `GET /orders/{orderId}` (단건)만 존재. `OrderRepository`에 회원 기준 조회 메서드도 없음 | `GET /api/v1/members/me/orders` (페이징). 응답은 `OrderResponse` 재사용 가능 | 주문 |
| P0-2 | **카테고리별 상품 조회** | `GET /products`가 `page`, `size`, `keyword`만 받음 | `categoryId` 파라미터 추가. 중분류 지정 시 해당 상품, 대분류 지정 시 하위 중분류 전체 | 상품 |
| P0-3 | **상품 이미지 조회** | `POST/DELETE /products/{id}/images`만 존재 | `GET /products/{id}/images` + 상품 목록 응답(`ProductListResponse`)에 대표 이미지 URL 포함 | 상품 |
| P0-4 | **상품 목록에 재고 정보** | `ProductListResponse`가 `productId`, `productName`, `productPrice`만 반환 | `availableStocks` 추가 → 목록에서 품절 배지 표시 가능 | 상품 |

### P0-1 상세: 주문 목록

구매자가 결제를 마치면 주문 상세로 이동하지만, 그 화면을 벗어나면 **주문번호를 기억하지 못하는 한 다시 접근할 수 없다.** 마이페이지에 주문 내역이 없는 쇼핑몰은 성립하지 않는다.

제안 인터페이스:

```
GET /api/v1/members/me/orders?page=0&size=10
→ PageResponse<OrderResponse>   (인증 필요, 본인 주문만)
```

- `OrderRepository.findAllByMemberIdOrderByIdDesc(Long memberId, Pageable)` 추가
- 프론트는 `/me`에 주문 내역 섹션을 붙이면 끝 (화면 구조는 이미 준비돼 있음)

### P0-2 상세: 카테고리 필터

관리자가 대분류 → 중분류를 만들고 상품을 중분류에 등록하는 구조를 갖췄지만, 정작 구매자가 **카테고리로 탐색할 수 없다.** 카테고리 기능 전체가 사용되지 않는 상태다.

```
GET /api/v1/products?categoryId=3&page=0&size=12
```

## 3. P1 — 있어야 제대로 굴러감

| # | 항목 | 현재 상태 | 필요한 것 | 담당 |
|---|------|-----------|-----------|------|
| P1-1 | **쿠폰·포인트 결제 적용** | 발급·조회만 가능. 결제와 연결되지 않음 | 주문 생성 API에 `couponId`, `usePoints` 추가 → 서버가 검증·계산해 할인 반영된 최종 금액을 주문 `totalPrice`로 저장. 결제는 그 금액으로 승인 (**팀 합의 완료**, 4절 참고) | 주문 + 쿠폰/포인트 |
| P1-2 | **발급 가능한 쿠폰 목록** | `POST /coupons/{id}/issue`, `GET /members/me/coupons`만 존재 | `GET /api/v1/coupons` — 무엇을 받을 수 있는지 알 방법이 없다 | 쿠폰 |
| P1-3 | **이벤트 목록** | `POST /events/{id}/participate`만 존재 | `GET /api/v1/events` — 어떤 이벤트가 열렸는지 알 방법이 없다 | 이벤트 |
| P1-4 | **관리자 승격 기능** | 승격 API 없음. `UPDATE members SET role='ADMIN'` DB 수동 변경 + 재로그인이 유일한 방법 | Admin 화면의 회원 관리 탭 + `PATCH /api/v1/admin/members/{id}/role` (ADMIN 전용). 최초 관리자만 DB 부트스트랩 | 회원 |
| P1-5 | **카테고리 전체 트리 API** | `GET /categories`는 대분류만 반환. 중분류는 대분류 상세(`GET /categories/{id}`)에만 있음 | `GET /api/v1/categories/tree`. 현재 프론트가 대분류마다 상세를 호출해 트리를 조립(N+1) | 카테고리 |
| P1-6 | **리뷰 평균 평점·페이징** | 상품별 리뷰를 전체 목록으로 반환. 평균 평점 없음 | 상품 응답에 `averageRating`, `reviewCount` + 리뷰 목록 페이징 | 리뷰 |
| P1-7 | **상품 정렬** | 정렬 조건 없음 | `sort` 파라미터 (최신순 / 가격 낮은순 / 높은순) | 상품 |

### P1-4 상세: 관리자 승격

현재 관리자 권한을 얻는 절차:

```
1. 카카오로 로그인 (role=USER로 가입)
2. 개발자가 DB에서 UPDATE members SET role='ADMIN' WHERE member_id=?
3. 로그아웃 후 재로그인 (권한이 JWT에 새겨지므로 새 토큰 필요)
```

실서비스 구조는 "**최초 관리자만 수동 지정, 이후는 관리자가 관리자를 임명**"이다. 모두가 스스로 승격할 수 있으면 권한이 의미를 잃는다.

## 4. 팀 합의 사항: 쿠폰·포인트 결제 적용 (2026-07-27)

결제 파트는 **"서버가 저장한 주문 금액 == 토스 승인 금액"** 으로 검증한다(금액 위변조 방지). 따라서 할인은 결제 시점이 아니라 **주문 생성 시점**에 적용한다.

```
1. 주문 생성 API에 couponId, usePoints(nullable) 추가
2. 서버가 쿠폰 유효성·포인트 잔액을 검증하고 할인 반영된 최종 금액을 주문 totalPrice로 저장
   (원가·할인액도 별도로 남기면 정산·조회에 유리)
3. 결제는 그 금액으로 토스 승인 → 결제 파트 코드 수정 없음
4. 주문 취소·결제 실패 시 쿠폰·포인트 복구 필요 (재고 예약→해제와 같은 패턴)
```

미해결 논점:

- **포인트 전액 결제(0원)** 는 토스 승인이 불가하다. 별도 분기 또는 "최소 결제 금액" 제약이 필요하다.
- **환불 시 쿠폰 복구 정책** — 사용한 쿠폰을 되살릴지 소멸시킬지 정해야 한다.

## 6. 이번 점검에서 해결한 것

| 항목 | 내용 | 커밋 |
|------|------|------|
| 결제 재시도 불가 | 토스는 `orderId`를 영구 유일값으로 취급해 재사용할 수 없다. `ORDER_{주문PK}` 고정 생성이라 결제 실패 후 재시도가 원천 차단됐다(`DUPLICATED_ORDER_ID`). `ORDER_{주문PK}_{타임스탬프}` 규칙으로 변경하고, 서버가 접두사로 주문 소유를 검증 | `68e39a2` |
| 결제 대기 주문 취소 시 재고 뻥튀기 | 재고 예약 모델 도입(2026-07-16) 이후 취소 로직이 갱신되지 않아, 예약만 잡힌 주문 취소에도 `increase()`를 호출해 실재고가 증가했다. 상태별로 `release`/`increase`를 분기 | `a771522` |
| 결제 완료 주문이 환불 없이 취소됨 | 취소 API로 `COMPLETED` 주문을 취소하면 재고만 복구되고 토스 결제는 취소되지 않아 **결제 금액이 환불되지 않았다.** 취소 API는 결제 대기 주문만 처리하고, 결제 완료 주문은 환불 API로 안내 | `20596b5` |
| 앱 기동 실패 요인 | `CategoryRepository.isEmpty()`는 Spring Data가 파생할 수 없는 메서드다. `application-local.yaml`의 mail 설정이 `datasource` 하위로 잘못 중첩돼 `spring.mail`로 인식되지 않았다 | `d0fc808` |
| 관리자 화면에 중분류 미표시 | `GET /categories`가 대분류만 반환하는 것을 몰라 발생. 프론트에서 대분류별 상세를 병렬 조회해 트리를 조립 | `ed902f5` |

**검증된 흐름** (실제 토스 결제 기준):

```
카카오 로그인 → 카테고리·상품 등록(Admin) → 바로구매(PENDING_PAYMENT + 재고 예약)
→ 토스 결제창 → 승인(COMPLETED + 재고 확정) → 결제 완료 이메일
```

## 7. 범위 밖 (실서비스 전환 시 필요)

이번 기준("동작하는 쇼핑몰")에는 포함하지 않되, 실서비스라면 반드시 필요한 항목이다.

- **배송지 관리** — 도메인 자체가 없다. 주문에 수령인·주소·연락처가 없어 실제 배송이 불가능하다.
- **배송 상태** — `OrderStatus`가 `PENDING_PAYMENT / COMPLETED / CANCELED / PAYMENT_FAILED` 4가지뿐이다. 배송 준비·배송중·배송완료 단계가 없다.
- **위시리스트(찜)** — 없다.
- **상품 이미지 다중 등록** — 현재 상품:이미지가 1:1 제약이다.

## 8. 참고: 로컬 실행 방법

```bash
# 1. 인프라 (MySQL + Redis)
docker compose up -d          # soldout DB 자동 생성
docker compose ps             # healthy 확인
docker compose down -v        # DB 완전 초기화가 필요할 때

# 2. 백엔드 — IntelliJ 실행 또는
./gradlew bootRun

# 3. 프론트엔드
cd frontend-v2 && npm install && npm run dev   # http://localhost:5173
```

필요한 환경 변수:

- 루트 `.env`: `MYSQL_*`, `KAKAO_*`, `JWT_SECRET`, `TOSS_SECRET_KEY`, `MAIL_USERNAME`, `MAIL_PASSWORD`
- `frontend-v2/.env`: `VITE_TOSS_CLIENT_KEY` (백엔드 `TOSS_SECRET_KEY`와 **같은 상점**의 키)

주의:

- 관리자 기능을 쓰려면 DB에서 `role='ADMIN'`으로 변경한 뒤 **재로그인**해야 한다(P1-4).
- 토스 테스트 환경에는 전용 테스트 카드번호가 없다. 본인 카드로 결제해도 실제 출금되지 않는다.
- 프론트엔드는 두 개가 공존한다. `frontend`(기존), `frontend-v2`(신규, 포트 5173). 동시 실행은 포트가 충돌한다.
