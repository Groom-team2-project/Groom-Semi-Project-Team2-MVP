## 3. 해석

### 3-1. 캐시는 제 값을 한다 — 조회 처리량 13.4배

| | 처리량 | p99 |
|---|---:|---:|
| 캐시 미스 | 805 ops/s | 60.1ms |
| 캐시 히트 | 10,828 ops/s | 5.0ms |
| **차이** | **13.4배** | **12분의 1** |

장바구니 조회는 회원·항목·상품을 조인하는 쿼리라 미스 비용이 크다. 캐시가 이걸 거의 전부 걷어낸다. 조회가 압도적으로 많은 장바구니 특성상 캐싱 설계는 유지할 가치가 충분하다.

> **단, 리뷰의 M2가 아직 남아 있다.** 캐시에 상품명·가격 **스냅샷**이 30분간 보관되는데 상품 가격이 바뀌어도 무효화되지 않는다. 위 수치는 "그 대가로 얻는 이득"의 크기를 보여줄 뿐, stale 문제를 정당화하지는 않는다.

### 3-2. 락 추가 비용은 사실상 0

리뷰에서 `useCoupon`·`addItem`·포인트 변동에 비관적 락을 추가했다. 락은 공짜가 아니므로 처리량 저하를 예상했으나, **경합이 없는 정상 트래픽에서는 측정 가능한 저하가 없었다.**

| 시나리오 | 수정 전 | 수정 후 | 비고 |
|---|---:|---:|---|
| 장바구니 담기 (회원별 독립) | 499.7 ops/s (실패 33) | 605.6 ops/s (실패 0) | 교착 제거로 오히려 상승 |
| 포인트 적립 (회원별 독립) | 619.5 ops/s (실패 41) | 594.7 ops/s (실패 0) | 오차 범위 |

락은 **같은 자원을 건드릴 때만** 대기시킨다. 서로 다른 회원의 요청은 서로 다른 행을 잠그므로 영향이 없다. "동시성 안전 = 느림"이라는 통념이 이 규모에서는 성립하지 않는다.

### 3-3. 경합이 집중되면 약 1/4 — 정상적인 대가

| 시나리오 | 독립 대비 |
|---|---:|
| 장바구니 담기 (한 회원 집중) | 0.24배 |
| 포인트 적립 (한 회원 집중) | 0.22배 |

32스레드가 **같은 회원 한 명**의 장바구니/잔액에 몰리는 극단적 상황이다. 직렬화되므로 처리량이 떨어지는 것이 **정상이고 의도된 동작**이다. 이 대가를 치르지 않으면 수량·잔액이 유실된다.

실사용에서 한 회원이 초당 수십 번 담기를 누르는 일은 없으므로, 이 수치는 상한을 보여주는 참고값이다.

### 3-4. 병목은 체크아웃 — 41.6 ops/s, p99 794ms

가장 느린 구간이다. 5개 품목 각각에 대해 재고 행 비관적 락을 순차로 잡고, 주문·주문항목·재고이력을 적재하기 때문이다.

- **현재는 정합성이 우선**이므로 이 구조가 맞다.
- 다만 실서비스에서 체크아웃 부하가 예상된다면 별도 튜닝 대상이다. `orderItemRepository.save()` / `stockHistoryRepository.save()`의 **배치 insert**(`hibernate.jdbc.batch_size`)가 가장 손쉬운 개선안이다.

### 3-5. 쿠폰 발급 149 ops/s — 구조적 상한

선착순 쿠폰은 **단일 쿠폰 행**의 `issuedQuantity`를 증가시키므로 전 요청이 한 행에 직렬화된다. 149 ops/s는 이 구조에서 나올 수 있는 상한에 가깝다. 대규모 선착순 이벤트를 감당하려면 Redis 카운터 선차감 같은 다른 설계가 필요하며, 현재 MVP 규모에서는 과한 최적화다.

## 4. 성능 테스트가 잡아낸 결함

이번 측정의 **가장 큰 성과는 숫자가 아니라 결함 발견**이다.

첫 실행에서, 공유 자원이 전혀 없어야 할 "회원별 독립" 시나리오에서 실패가 나왔다.

```
[장바구니 담기 (회원별 독립)] 실패 33건 — MySQLTransactionRollbackException: Deadlock found
[포인트 적립 (회원별 독립)]   실패 41건 — MySQLTransactionRollbackException: Deadlock found
```

### 원인 — 없는 행을 잠그면 갭 락이 잡힌다

`getOrCreate...WithLock` 패턴이 **아직 존재하지 않는 행**을 `SELECT ... FOR UPDATE` 하고 있었다. InnoDB는 이때 레코드 락이 아니라 **갭 락(gap lock)** 을 잡는다.

1. 갭 락끼리는 서로 **공존**한다 → 여러 트랜잭션이 동시에 같은 갭을 잡는다.
2. 그런데 뒤따르는 INSERT의 **insert-intention 락**은 남이 쥔 갭 락과 **충돌**한다.
3. 결과: 서로 다른 회원의 첫 담기/첫 적립끼리도 서로의 갭 락을 기다리며 **교착**.

### 조치

**반드시 존재하는 회원 행**을 잠근 뒤 장바구니/잔액을 읽도록 바꿨다. 회원 행은 실재하므로 레코드 락만 잡히고 갭 락이 없다.

**순서가 핵심이다.** REPEATABLE READ의 읽기 뷰는 첫 *일반* 읽기에서 만들어지고 **락 조회는 읽기 뷰를 만들지 않는다.** 따라서 락을 먼저 잡고 읽어야 앞선 홀더가 커밋한 행이 보인다. 반대로 읽고 나서 잠그면 낡은 스냅샷을 보고 중복 생성을 시도한다.

```
33건 / 41건  →  0건 / 0건   (처리량 저하 없음)
```

### 폐기한 대안 — `REQUIRES_NEW`

중간에 "별도 트랜잭션에서 먼저 만들어 두기"를 시도했다가 되돌렸다. `REQUIRES_NEW`는 바깥 트랜잭션의 커넥션을 **쥔 채** 두 번째 커넥션을 요구하므로, 스레드당 커넥션 2개가 필요하다. 기본 풀 크기(10)에서 20스레드가 몰리자 **풀이 고갈되어 30초 타임아웃까지 행**이 걸렸다. 교착을 더 나쁜 행으로 바꾸는 셈이라 폐기했다.

## 5. 왜 H2가 아니라 MySQL로 측정했는가

**H2에는 갭 락 개념이 없다.** 위 교착은 H2 기반 기존 테스트에서 20스레드를 돌려도 **전혀 드러나지 않았다.** 실제로 그 코드는 H2 테스트를 모두 통과한 상태로 이미 커밋되어 있었다(`4398df4`).

> **동시성 관련 변경은 H2 그린만으로 검증했다고 말할 수 없다.**
> 반드시 실제 MySQL로 다시 돌려야 한다.

또한 부하 테스트 하네스는 **실패를 삼키지 말고 예외 유형별로 집계해 출력해야 한다.** 처리량 표만 봤다면 "500 ops/s 나오네" 하고 넘어갔을 것이고, 교착 33건은 영영 발견되지 않았다.

## 6. 측정 방법론 메모

- **워밍업 분리**: 시나리오당 50회를 먼저 돌려 JIT·커넥션풀·하이버네이트 캐시를 데우고, 측정에서 제외한다.
- **동시 시작 정렬**: `CountDownLatch` 3개(ready/start/done)로 모든 스레드가 같은 순간에 출발하도록 맞춘다. 스레드 생성 시간이 측정에 섞이지 않는다.
- **지연시간은 백분위로**: 평균만 보면 꼬리 지연이 가려진다. p50/p95/p99를 함께 본다.
- **유실 검증 동반**: 처리량과 함께 "성공 횟수만큼 실제로 반영됐는가"를 단언한다. 워밍업분이 섞이지 않도록 측정 구간의 **증가분**만 비교한다.
- **절대 수치는 환경 의존적**이다. 의미 있는 비교는 "같은 장비에서 수정 전/후" 또는 "캐시 히트 vs 미스" 같은 **상대값**이다. 그래서 이 테스트는 임계값 단언을 두지 않는다.

## 7. 후속 과제

| 우선순위 | 항목 | 근거 |
|---|---|---|
| 높음 | 캐시 stale (리뷰 M2) | 상품 가격 변경 시 장바구니 캐시가 최대 30분 옛 가격 노출. 캐시 이득(13.4배)이 큰 만큼 무효화 연동을 제대로 붙일 가치가 있다 |
| 중간 | 체크아웃 배치 insert | 41.6 ops/s로 가장 느린 구간. `hibernate.jdbc.batch_size` 적용이 최소 비용 개선안 |
| 중간 | 스케줄러 다중 인스턴스 | 예약 재고 회수 스케줄러를 여러 대에서 돌리면 락 경합 발생. 한 대만 켜거나 분산 락 적용 (`pre-deploy-checklist.md` §7) |
| 낮음 | 쿠폰 발급 149 ops/s | 대규모 선착순 이벤트 시에만 문제. 현 MVP 규모에서는 과한 최적화 |

## 8. 이 측정 이후 반영된 변경

이 보고서의 수치는 아래 변경이 **모두 반영된** 최종 코드로 측정한 값이다.

- 리뷰 C1~C4 · H1~H4 수정 (동시성·멱등성·검증)
- §4 의 갭 락 교착 수정
- M1: 체크아웃의 삭제 상품 검증
- M3: 예약 재고 회수 스케줄러 (`ReservationExpiryScheduler`)
- L1~L5: Swagger 노출·회원 응답 축소·`final` 컬렉션 제거·유니크 제약 검증·회원 부재 구분
- 마이페이지 주문 내역 API (`GET /api/v1/members/me/orders`)

M1·M3 은 체크아웃 경로에 검사와 신규 스케줄러를 추가하지만, 측정값(체크아웃 41.6 ops/s)은 추가 전과
오차 범위 내로 동일하다. 삭제 상품 검사는 이미 로드된 엔티티의 필드 비교이고, 스케줄러는 테스트 중
비활성화(`cart.reservation.expiry.enabled=false`)되어 측정에 개입하지 않는다.

자세한 결함 목록과 조치는 [member-cart-point-design.md](member-cart-point-design.md) §5 참고.
