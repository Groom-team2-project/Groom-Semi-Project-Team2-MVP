# 선착순 이벤트 락 성능 비교

- 측정 일시: 2026-07-28 16:39 KST
- 환경: 애플리케이션 1개, Java 21.0.11, Docker Engine 29.3.1,
  Docker MySQL 8.4/Redis 7.2/k6 0.54.0
- 부하: VU 100, 실행당 요청 500건, 전략별 3회
- 대상: 같은 선착순 이벤트 참여 로직의 Redisson 분산락과 MySQL 비관적 쓰기 락
- 조건: 이벤트 정원 500명, 요청마다 서로 다른 회원 ID 사용
- 실행 순서: 비관적 락 측정 후 분산락 측정

## 중앙값 비교

| 전략 | 처리량(req/s) | 평균 응답(ms) | p95(ms) | p99(ms) |
|---|---:|---:|---:|---:|
| 비관적 락 | 135.62 | 663.54 | 820.69 | 834.17 |
| 분산락 | 92.46 | 955.35 | 1,114.94 | 1,138.47 |

비관적 락은 분산락보다 처리량 중앙값이 46.68% 높았고, p95 응답 시간 중앙값은
26.39% 낮았다. 이 환경에서는 애플리케이션과 MySQL이 한 인스턴스씩이므로 Redis를
추가로 왕복하고 애플리케이션 레벨에서 요청을 직렬화하는 분산락의 비용이 더 크게 나타났다.

두 전략 모두 총 1,500건의 측정 요청을 오류 없이 처리했다. 모든 실행에서 이벤트의
`participatedCount`와 참여 테이블 행 수가 500으로 일치했고 정원도 초과하지 않았다.
따라서 이번 조건에서는 두 방식 모두 정합성을 지켰으며, 성능은 비관적 락이 우세했다.

## 해석 시 주의사항

- 이 결과는 로컬 단일 호스트의 상대 비교이며 운영 환경의 절대 처리량이 아니다.
- 애플리케이션, MySQL, Redis, k6가 같은 호스트의 CPU와 디스크를 공유한다.
- 분산락의 핵심 장점인 여러 애플리케이션 인스턴스 간 조정 능력은 이번 측정에 포함되지 않았다.
- HTTP, JSON, JPA, DB 저장 비용을 포함한 엔드투엔드 측정이며 락 명령만의 마이크로벤치마크가 아니다.
- 각 전략은 워밍업 후 측정했지만 실행이 반복될수록 JVM 및 DB 캐시 효과로 처리량이 증가했다.
  단일 실행값보다 3회 중앙값을 비교 기준으로 삼은 이유다.

## 결론

현재처럼 애플리케이션과 DB가 각각 단일 인스턴스이고 하나의 DB 행을 갱신하는 구조에서는
비관적 락이 더 단순하고 빨랐다. 다중 애플리케이션 인스턴스에서 DB 밖의 공유 자원까지
보호해야 한다면 분산락의 필요성이 생기므로, 그 경우에는 애플리케이션을 2개 이상 띄운
추가 측정으로 판단해야 한다.
