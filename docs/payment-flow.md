# 결제 흐름 설계

SoldOut의 결제는 **"재고를 언제 잠그고, 언제 확정하고, 언제 풀 것인가"** 를 결정하는 문제다.
한정판 커머스라 재고가 곧 상품이고, 결제는 외부 시스템(토스페이먼츠)에 의존해 언제든 실패하거나 응답이 사라질 수 있다.

이 문서는 그 흐름과, 그렇게 설계한 이유를 정리한다.

---

## 1. 핵심 아이디어: 재고를 3개 축으로 관리한다

주문 시점에 실제 재고를 깎으면 결제 실패 때마다 복구해야 하고, 깎지 않으면 여러 사람이 같은 물건을 결제한다.
그래서 재고를 **실재고**와 **예약분**으로 나눠 관리한다.

```
stocks            실제 보유 재고
reservedStocks    결제 대기 중 잡아둔 수량
availableStocks   = stocks - reservedStocks   (지금 새로 팔 수 있는 수량)
```

| 연산 | stocks | reservedStocks | 언제 |
|------|--------|----------------|------|
| `reserve` | — | **+** | 주문 생성 (결제 전 찜) |
| `confirm` | **−** | **−** | 결제 성공 (판매 확정) |
| `release` | — | **−** | 결제 실패·만료 (찜 해제) |
| `increase` | **+** | — | 환불·입고 (실재고 복구) |

재고 변경은 모두 `stock_histories` 에 이력을 남긴다: `RESERVE / CONFIRM / RELEASE / RESTORE / INBOUND / DECREASE`

> **왜 이렇게 나눴나:** 예약만 잡아두면 결제 실패 시 실재고를 건드리지 않았으므로 **되돌릴 것이 없다**.
> 판매 확정은 결제 성공이라는 하나의 시점에서만 일어나, 재고와 돈이 어긋날 여지가 줄어든다.

## 2. 주문 상태 흐름

```
                    ┌──────────────────┐
   주문 생성 ──────▶ │ PENDING_PAYMENT  │  예약만 잡힌 상태 (만료 대상)
                    └────┬────────┬────┘
              결제 시작   │        │  사용자 취소 / 30분 만료
                        ▼        ▼
          ┌───────────────────┐  ┌──────────┐
          │PAYMENT_PROCESSING │  │ CANCELED │  예약 해제(release)
          │  (만료 대상 아님)   │  └──────────┘
          └───┬───────────┬───┘
    승인 성공  │           │  승인 거절 / 사용자가 결제창 취소
             ▼           └────────▶ PENDING_PAYMENT 로 복귀
      ┌───────────┐                (예약 유지 → 만료 전까지 재시도 가능)
      │ COMPLETED │  재고 확정(confirm)
      └─────┬─────┘
            │  환불
            ▼
      ┌──────────┐
      │ CANCELED │  실재고 복구(increase) + 토스 결제 취소
      └──────────┘
```

**상태별 규칙**

| 상태 | 재고 | 취소 가능 | 만료 대상 |
|------|------|-----------|-----------|
| `PENDING_PAYMENT` | 예약됨 | ✅ (예약 해제) | ✅ 30분 |
| `PAYMENT_PROCESSING` | 예약됨 | ❌ | ❌ (정산이 담당) |
| `COMPLETED` | 확정됨 | ❌ 취소 API 불가 → **환불 API로만** | — |
| `CANCELED` | 해제/복구됨 | ❌ | — |

핵심 정책 두 가지:

- **결제 거절은 주문 취소가 아니다.** 카드가 거절되거나 사용자가 결제창을 닫으면 "이 시도만" 실패한 것으로 보고
  `PENDING_PAYMENT` 로 되돌린다. 예약이 유지되므로 만료 전까지 다른 결제 수단으로 재시도할 수 있다.
- **결제 완료 주문은 취소 API로 취소할 수 없다.** 취소 API는 재고만 복구하고 토스 결제는 취소하지 않아,
  돈을 돌려주지 않은 채 주문이 종료된다. 환불 API(`POST /orders/{id}/payments/refund`)로만 처리한다.

## 3. 결제 승인은 트랜잭션을 3개로 쪼갠다

### 문제

처음에는 `pay()` 하나를 `@Transactional` 로 감쌌다. 그런데 그 안에서 토스 승인(외부 HTTP, 수 초)을 호출한다.

```
1. pay() 가 주문(PENDING_PAYMENT)을 락 없이 읽음   ← findById
2. 토스 confirm 호출 — 수 초 소요
3. 그사이 만료 스케줄러가 주문을 잠그고 예약 해제 + 주문 취소 → 커밋
4. 토스가 "승인 성공" 반환
5. 재고를 확정하려는데 예약이 이미 0 → 예외 → 롤백
```

**결과: 토스는 결제 성공(= 돈을 받음), DB는 주문 취소.**

### 해결하지 않은 선택지

**주문에 락을 걸고 승인 호출 내내 잡고 있기** — 스케줄러는 막히지만, 외부 호출 수 초 동안 DB 락과 커넥션을
붙잡는다. 동시 결제가 몰리면 커넥션 풀이 마른다.

### 채택한 구조

승인 요청 **전에** 상태를 바꿔 커밋하고, 외부 호출은 트랜잭션 밖에서 한다.

```
PaymentService.pay()               ← @Transactional 없음. 오케스트레이션만
  │
  ├─ ① begin()        [TX] PENDING_PAYMENT → PAYMENT_PROCESSING 커밋
  │                        + 시도 이력(PaymentAttempt) 저장
  │                        커밋해야 스케줄러가 이 주문을 조회 대상에서 뺀다
  │
  ├─ ② 토스 confirm    락·트랜잭션 없이 호출
  │
  └─ ③ complete()     [TX] 재고 확정 + 주문 완료 + 결제 저장 + 이벤트 발행
      revert()        [TX] 승인 실패 시 결제 대기로 복귀
```

구현상 주의점:

- **같은 클래스 안에서 호출하면 트랜잭션이 분리되지 않는다.** 스프링 프록시를 지나지 않기 때문이다.
  그래서 오케스트레이션(`PaymentService`)과 단계 실행(`PaymentAttemptService`)을 다른 빈으로 나눴다.
- **승인 금액은 서버가 보관한 주문 금액만 사용한다.** `pay()` 는 트랜잭션이 없어 주문을 읽지 못하므로,
  `begin()` 이 금액을 함께 돌려준다. 클라이언트가 보낸 금액은 신뢰하지 않는다.

부수 효과로 **중복 클릭 방어**가 생겼다. 첫 클릭이 `PAYMENT_PROCESSING` 으로 바꾸므로,
두 번째 클릭은 `begin()` 의 `startPayment()` 에서 막힌다.

## 4. 결제 시도 이력을 따로 남긴다

승인 요청을 보낸 뒤 응답을 받지 못하면(타임아웃, 처리 중 서버 종료) 나중에 "토스에서는 결제가 됐는지"를
확인해야 한다. 그러려면 승인에 사용한 주문번호를 **요청 전에** 저장해둬야 한다.

```java
PaymentAttempt {
  orderId, tossOrderId(unique), paymentKey, amount, method,
  status: STARTED | SUCCEEDED | FAILED | NEEDS_REVIEW
}
```

**`Payment` 로는 이 역할을 할 수 없다.** `Payment.order_id` 에 UNIQUE 제약이 있어 주문당 한 건만 존재한다.
시도 시점에 `Payment` 를 만들면 카드 거절 후 재시도가 "이미 결제됨"으로 막힌다.
시도는 여러 번일 수 있으므로 이력을 별도 테이블로 뒀다.

### 토스 주문번호 규칙

```
ORDER_{주문PK}_{타임스탬프}     예: ORDER_42_1753622752458
```

- 토스는 `orderId` 를 **영구 유일값**으로 취급해 한 번 쓴 값을 재사용할 수 없다(`DUPLICATED_ORDER_ID`).
  고정값(`ORDER_42`)을 쓰면 결제 실패 후 재시도가 원천적으로 막힌다.
- 6~64자 제약도 있어 짧은 주문 PK 를 그대로 쓸 수 없다.
- 서버는 `ORDER_{주문PK}_` 접두사로 **이 주문번호가 해당 주문의 것인지 검증**한다.
  (다른 주문의 결제를 가로채지 못하게)

## 5. 정산: 결과를 알 수 없게 된 결제를 마무리한다

`PAYMENT_PROCESSING` 은 만료 대상이 아니다. 그래서 승인 응답을 받지 못하면 그 주문은 아무도 손대지 않고
**예약 재고가 영구히 잠긴다.** 반대로 무조건 풀어버리면 이미 결제된 주문을 취소한다.

그래서 토스에 **실제 결제 여부를 물어본 뒤에만** 처리한다. (`GET /v1/payments/orders/{orderId}`)

```
STARTED 로 5분 이상 방치된 시도를 찾는다
   │
   └─ 토스 조회
        ├─ 결제 이력 없음(404)      → 승인 요청이 닿지 않았다 → 결제 대기로 복귀
        ├─ 거절·만료(ABORTED 등)    → 결제되지 않았다 → 결제 대기로 복귀
        ├─ 금액 불일치              → 완료하지 않고 자동 환불 + 운영 확인
        ├─ DONE (결제 성공)
        │    └─ 주문을 잠그고 상태 재확인
        │         ├─ PAYMENT_PROCESSING (예약 남음) → 완료 재시도
        │         ├─ 이미 COMPLETED               → 시도만 정리 (중복 완료 방지)
        │         └─ 이미 종료(예약 해제됨)         → 자동 환불 + 운영 확인
        └─ 조회 자체 실패            → 아무것도 건드리지 않고 다음 주기
```

**설계 원칙**

- **조회 실패를 "결제 없음"으로 오판하면 안 된다.** 이미 결제된 주문을 취소해버릴 수 있다.
  그래서 404(결제 이력 없음)와 그 외 오류(조회 실패)를 명확히 구분한다.
- **판단은 주문을 잠근 상태에서, 상태를 다시 확인해서 한다.** 이 재확인이 없으면 중복 완료·중복 환불이 생긴다.
- **외부 호출(조회·환불)은 트랜잭션 밖에서** 한다. 3절과 같은 이유다.
- **자동 환불까지 실패하면 재시도하지 않는다.** 반복하면 중복 환불 위험이 있어
  `NEEDS_REVIEW` 로 표시해 정산 대상에서 빼고 사람이 판단하게 한다.

### 시간 설계

| 값 | 기본 | 설정 키 |
|----|------|---------|
| 결제 만료 (예약 회수) | 30분 | `cart.reservation.expiry.timeout` |
| 정산 대상 판단 | 5분 | `payment.reconciliation.timeout` |
| 두 스케줄러 주기 | 1분 | `*.interval` |

**정산 타임아웃(5분)은 예약 만료(30분)보다 짧아야 한다.** 그래야 결제가 성공했는데 반영되지 않은 주문을
예약이 풀리기 전에 완료 처리할 수 있다. 반대로 너무 짧으면 정상 진행 중인 승인을 정산이 먼저 집어 경합이 생긴다.

## 6. 결제 완료 후: 이벤트로 후속 처리를 분리한다

결제 완료 시 이메일을 보내야 하는데, 이를 `pay()` 안에서 직접 호출하면
① 결제 로직에 알림 책임이 섞이고 ② 메일 서버가 느리거나 실패하면 결제까지 영향받는다.

```
결제 성공 → PaymentCompletedEvent 발행
              ↓
    @TransactionalEventListener(AFTER_COMMIT)
              ↓
    회원 이메일 조회 → 결제 완료 메일 발송
```

- `AFTER_COMMIT` 이므로 **결제가 DB에 커밋된 뒤에만** 실행된다. 롤백되면 메일이 나가지 않는다.
- 메일 발송 실패는 로그만 남긴다. 알림은 부가 기능이지 결제 성패를 좌우해서는 안 된다.

## 7. 실제로 발견하고 고친 문제들

모두 **실제 토스 테스트 결제를 돌려보면서** 드러났다. 코드만 읽어서는 보이지 않았다.

### ① 결제 재시도가 아예 불가능했다 (`68e39a2`)

토스가 `DUPLICATED_ORDER_ID` 를 반환했다. `orderId` 를 `ORDER_{주문PK}` 로 고정 생성해서,
한 번 결제창까지 갔다가 실패한 주문은 **다시 결제할 방법이 없었다.**
카드 한도 초과로 실패한 사용자가 재시도조차 못 하는 상태였다.

→ `ORDER_{주문PK}_{타임스탬프}` 로 변경. 서버는 접두사로 주문 소유를 검증한다.

### ② 결제 대기 주문 취소 시 실재고가 늘어났다 (`a771522`)

재고 예약 모델이 나중에 도입됐는데 취소 로직이 따라가지 않아, 예약만 잡힌 주문을 취소할 때도
`increase()` 를 호출했다.

```
재고 10개, 3개 주문(예약) 상태에서 취소
  기대: stocks 10 유지, reserved 3 → 0
  실제: stocks 10 → 13   ❌ 팔지도 않은 재고가 늘어남
```

→ 취소 전 상태로 분기. 예약 주문은 `release`, 결제 완료 주문은 `increase`.

### ③ 결제 완료 주문을 취소하면 돈이 환불되지 않았다 (`35add2f`)

취소 API는 재고를 복구하고 주문을 `CANCELED` 로 바꾸지만 **토스 결제는 취소하지 않았다.**
결과적으로 돈은 받은 채 주문만 종료됐다.

→ 취소 API는 결제 대기 주문만 처리하고, 결제 완료 주문은 `ORDER_REFUND_REQUIRED` 로 환불 API를 안내한다.

### ④ 승인 중 만료로 결제와 주문이 어긋날 수 있었다 (`ebd5db5`, `bb4fa3c`)

3절·5절의 내용. 팀 리뷰에서 제기된 문제로, 코드를 확인해 재현 경로가 실재함을 확인한 뒤
상태 분리 + 정산으로 해결했다.

## 8. 테스트 전략

| 대상 | 방식 | 확인하는 것 |
|------|------|-------------|
| 상태 전이 | 단위 (Mockito) | 중복 클릭 차단, 다른 주문번호 거부, 실패 시 복귀 |
| 오케스트레이션 | 단위 (`InOrder`) | "상태 전이 → 승인 → 반영" 순서 보장 |
| 정산 분기 | 단위 | 7가지 경로 (조회실패/이력없음/거절/복구/환불/환불실패/금액불일치) |
| 토스 연동 | `MockRestServiceServer` | 요청 헤더·URL, 404와 그 외 오류 구분 |
| **만료 경합** | 통합 (`@SpringBootTest`) | 승인 중 주문이 만료 대상에서 제외되는지 |
| 동시성 | 통합 (100 스레드) | 동시 취소 100건 중 1건만 성공 |
| **결제 흐름** | 실제 토스 결제 | 로그인 → 주문(예약) → 승인(확정) → 완료 메일 |
| **정산 흐름** | 실제 토스 조회·환불 | 아래 참고 |

**테스트가 실제로 결함을 잡는지 검증했다.** 수정 코드를 되돌리면 해당 테스트가 실패하는 것을 확인했다.
통과하는 테스트를 쓰는 것과, 버그를 잡는 테스트를 쓰는 것은 다르다.

### 정산 E2E 검증 결과

정산 타임아웃을 10초로 낮추고, 승인 응답을 받지 못한 상태(`PAYMENT_PROCESSING` + 시도 `STARTED`)를
만들어 두 갈래를 실제로 확인했다.

**① 토스에 결제 이력이 없는 경우 → 결제 대기로 복귀**

```
스케줄러: 결제 정산 대상 1건을 처리합니다.
정산    : 토스에 결제 이력이 없어 결제 대기로 되돌립니다. attemptId=1

결과: 주문 PAYMENT_PROCESSING → PENDING_PAYMENT
      시도 STARTED → FAILED
      재고 10 / 예약 2 유지 → 재시도 가능 (주문을 취소하지 않음)
```

**② 결제는 성공했지만 주문이 이미 종료된 경우 → 자동 환불**

실제로 승인이 완료된 결제(`ORDER_5_...`, 100원, `DONE`)를 대상으로, 주문을 취소 상태로 만들어 재현했다.

```
정산: 결제는 성공했지만 주문이 이미 종료된 상태입니다. 환불이 필요합니다. orderId=5, status=CANCELED
정산: 결제 시도에 운영 확인이 필요합니다. attemptId=2,
      reason=주문이 이미 종료되어 자동 환불 — 자동 환불 완료

토스 조회 결과: status=CANCELED, 취소 1건, 사유 "결제 성공 후 주문 반영 실패 (자동 환불)", 금액 100
시도 이력: NEEDS_REVIEW
```

**토스에서 실제로 환불이 이루어진 것까지 확인했다.** 자동 환불은 돈이 오가는 동작이라
로그만으로 판단하지 않고 결제사 상태를 직접 조회해 검증했다.

## 9. 남은 과제

- **장바구니 주문에 만료 시각이 없다** — `CartOrderService` 가 `paymentExpiresAt` 을 설정하지 않아
  스케줄러가 잡지 못한다. 단건 구매 경로만 반영돼 있다.
- **쿠폰·포인트 결제 적용** — 주문 생성 시 할인을 반영한 최종 금액을 저장하는 방향으로 합의됨.
  포인트 전액 결제(0원)는 토스 승인이 불가해 별도 처리가 필요하다.
- **스케줄러 단일 인스턴스 전제** — 여러 대로 배포하면 분산 락이 필요하다.
